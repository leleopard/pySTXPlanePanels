## EPIC 7 — Bendix-King Radio Stack

**As a user, I want the five Bendix-King radios from `pyXPPanels/RadioStack.py` rendered as a YAML-driven panel, driven entirely by X-Plane datarefs (no Arduino input, no Python-side state machines).**

The original implementation mixed Arduino-input handling and a few Python-side state machines (e.g. ADF timer mode tracked by listening to X-Plane commands). For this rewrite the panel must be **display-only**: every visible state derived from a dataref X-Plane already publishes. Where the original used `registerXPCmdCallback`-style logic, we re-evaluate whether the underlying state has a dataref source before re-introducing any panel-side state.

**GLASS-07 note:** the altitude tape (B737-02) needed three near-identical convert functions — `return_hundreds_digit_20ft`, `return_thousands_digit_20ft`, `return_ten_thousands_digit_20ft` — each hardcoding a blend window (80→100, 980→1000, 9980→10000) tied to one specific instrument's drum resolution. A fourth drum at a different resolution means a fourth hardcoded function. Worth exploring a generic mechanism (e.g. a `digit_rollover` convert function that takes its place-value and blend-window-width as YAML parameters instead of being baked into the function name/body) so this scales without growing `convert.py` per instrument.

**GLASS-10 note:** `NeedleGauge` linear mode originally walked from the spacing table's min to max value at a fixed interval, interpolating a position for any value that wasn't an explicit breakpoint — so extending a table from `[1, 2]` to `[1, 2, 6]` silently grew unwanted interpolated ticks at 3, 4, 5 too. Fixed by making every table row an explicit, fully-styled tick with no interpolation (GLASS-09). Going forward there will be two deliberate patterns: **explicit** (current — hand-list exactly the ticks/labels you want, non-uniform spacing included) for scales like a real-world VSI that don't follow a formula, and **interval-based** (this backlog item) for the common case of "draw a tick every N units across a range" without hand-listing every row. These should coexist as two distinct, clearly-named modes rather than the previous implicit hybrid that surprised the user.

## EPIC 12 — Interactive Panel Controls

Adds mouse and touchscreen interactivity to the panel. The panel remains a UDP consumer for dataref data; it additionally sends X-Plane commands via `pyxpudpserver.sendXPCmd()` (already implemented in the library). Visual state of all controls is driven by datarefs — no local state. Interactive components are **invisible overlays**; appearance is handled by companion visual components (ImagePanel, FilledRect, etc.) driven by datarefs as normal.

### Architecture decisions

| Decision | Choice |
|---|---|
| Send mechanism | `pyxpudpserver.sendXPCmd()` / `sendXPDref()` — already in the library, no new sender needed |
| State truth | X-Plane datarefs only. Controls read state; they never own it |
| Optimistic UI | Short-lived pending flag set on press, cleared when confirming dataref arrives or after 600 ms timeout |
| Visual rendering | Separate from interaction. Interactive components are invisible at runtime; designer shows dashed hit-zone overlays |
| Input model | `on_mouse_press/drag/release/scroll` as primary path (Pi touchscreen emulates mouse for single touch); `on_touch_*` handlers as thin pass-throughs to the same gesture dispatcher |
| Rotary gesture | Tap left half = CCW step · tap right half = CW step · drag up = CW continuous · drag down = CCW continuous · mouse scroll = 1 step/notch |
| Hit target size | `component.size × hit_padding_multiplier` (panel-level YAML key, default 1.5) |
| `send_cmd` wiring | A `Callable[[str], None]` is passed to interactive components at panel-load time alongside the existing `get_data`. No-op in `--test` mode |

### YAML schemas

```yaml
# Momentary button — fires command on press, optional command_end on release
- type: Momentary_Button
  name: ap_engage_btn
  position: [150, 200]
  size: [50, 30]
  command: sim/autopilot/autopilot_on
  command_end: sim/autopilot/autopilot_off   # optional: sent on release

# Switch — reads state_dataref to choose which command to send on tap
- type: Switch
  name: landing_light_sw
  position: [80, 150]
  size: [40, 60]
  command_on: sim/lights/landing_lights_on
  command_off: sim/lights/landing_lights_off
  state_dataref: sim/cockpit/electrical/landing_lights_on
  # or single toggle: command: sim/lights/landing_lights_on_off_toggle

# Rotary encoder — tap halves or drag
- type: RotaryEncoder
  name: heading_bug_knob
  position: [200, 300]
  size: [60, 60]
  command_cw: sim/autopilot/heading_up
  command_ccw: sim/autopilot/heading_down
  drag_px_per_step: 5   # pixels of drag before firing one command step

# Panel-level hit padding (top-level key in panel YAML)
hit_padding_multiplier: 1.5   # default if absent
```

## EPIC 13 — Moving Map / Navigation Data

A moving map layer for `VectorCompassRose`: airports, VORs, and NDBs plotted around the aircraft's own GPS position, rotating heading-up with the compass card, scaled to the same range the range rings already show. The position data comes from X-Plane's own installed nav database (`earth_nav.dat`, `apt.dat`), never from this repo — `earth_nav.dat` carries a Navigraph/Jeppesen copyright notice and this repo is public, so nothing is pre-shipped; the cache is generated locally, on demand, from the user's own X-Plane install.

### Architecture decisions

| Decision | Choice |
|---|---|
| Data source | User's own X-Plane install, parsed locally — never bundled/committed |
| Cache location | `Path.home() / ".pySTXPlanePanels" / "navdata_cache.json"` — outside any git working tree |
| Install path storage | `QSettings` (machine-local), not `config.yaml` — `config.yaml` is git-tracked and synced across the user's multiple PCs, and an install path is specific to whichever machine the designer runs on |
| Airport position | `apt.dat` row `1302 datum_lat`/`datum_lon`; falls back to the first runway/helipad endpoint (rows `100`/`101`/`102`) when those keys are present but empty, which is common for small/unmodeled fields |
| Scope | Airports, VORs, NDBs only (not ILS/DME/fixes/airways) |
| Precedence | Custom Data → Custom Scenery (or Global Scenery on XP12)/Global Airports → default data layers only; individually purchased scenery packs' own `apt.dat` are not enumerated |

### Stories

| ID | Story | Status |
|----|-------|--------|
| MAP-01 | As a developer, `gauge_core/navdata.py` streams X-Plane's `earth_nav.dat` (VORs/NDBs), `earth_fix.dat` (waypoints/fixes), and `apt.dat` (airports, position-only — never loading the 300+ MB file into memory at once) into a small local JSON cache, resolving X-Plane's own file precedence (Custom Data → Custom Scenery/Global Airports → default data). | ✅ |
| MAP-02 | As a developer, `gauge_core/geo.py` provides a flat-earth `bearing_distance_nm()` helper (equirectangular approximation, accurate enough for HSI-scale ranges) for converting a GPS lat/lon pair into the compass-bearing + NM-distance format every other rotating element on `VectorCompassRose` already consumes via `_point_at()`. | ✅ |
| MAP-03 | As a user, I can open Settings → Navigation Data… in the designer, point it at my X-Plane install folder, and regenerate the local nav data cache — the only place cache generation happens; the panel runtime just reads whatever cache already exists. | ✅ |
| MAP-04 | As a user, I can configure a `moving_map` block on a `VectorCompassRose` showing nearby airports/VORs/NDBs positioned by GPS coordinates relative to the aircraft, heading-up rotated, gated by a visibility dataref, drawn underneath the rest of the rose, and scaled to the same range `range_rings.label` already computes. | ✅ |
| MAP-05 | As a user, I can also show en-route waypoints/fixes (`moving_map.waypoint`) on the moving map, same styling convention as airports/VORs/NDBs. | ✅ |

- *2026-07-18* — fix(core+designer, cross-repo): datarefs subscriptions "hit and miss" when repeatedly testing instruments/panels — traced to two real, separate shutdown-cleanup gaps, both now fixed. **Root cause (in `pyxpudpserver`, the user's separate published package at `C:\Users\stephane\Desktop\pyXPUDPServer`, not tracked in this repo):** each dataref subscription gets its own dedicated UDP socket and X-Plane is told (via the RREF protocol) to push it forever at 30Hz — `quit()` only ever closed the *local* sockets, never sending X-Plane the RREF frequency=0 message that actually cancels a subscription, so X-Plane had no idea the client disconnected and kept trying to push every previously-subscribed dataref to now-dead local ports indefinitely; repeated open/close cycles while testing accumulate these orphaned subscriptions with no way to know they're unwanted, a strong candidate for progressively "hit and miss" behavior over a session. Fixed by giving `__sendRREFmessage()` an optional `frequency` param (default 30, unchanged for the existing subscribe/resubscribe call sites) and having `quit()` call it with `frequency=0` for every subscribed dataref index before closing any sockets. Verified with a real UDP round-trip test (a fake "X-Plane" socket receiving the actual wire packets): subscribing two datarefs produced two frequency=30 RREF packets as before, and `quit()` now produces two frequency=0 packets, one per previously-subscribed index, before the sockets close. **Second, separate gap (`gauge_designer`, in this repo):** `preview.py`'s `stop_live()` and three equivalent call sites in `instrument_view.py` (`stop_test`, `_on_harness_closed`, `stop_live`) all used `subprocess.Popen.terminate()` to stop a running `gauge_core.runner` child process — on Windows this calls `TerminateProcess()`, an abrupt kill that gives the child *zero* chance to run any cleanup at all, not even the (already insufficient) local socket close from the fix above. Confirmed this empirically before writing any fix: a synthetic child process's own `finally:` block never ran under either `terminate()` or `CTRL_BREAK_EVENT` (the exit code, `0xC000013A`/`STATUS_CONTROL_C_EXIT`, confirms Windows kills the process before Python's runtime can intervene) — but `taskkill /PID <pid>` (deliberately *without* `/F`) posts a `WM_CLOSE` to the process's own window, which pyglet/Arcade delivers as the normal `on_close` event, the exact same path a user clicking the window's own close button takes; confirmed exit code 0 and both `on_close()` and the process's `finally:` block running, using both a minimal synthetic Arcade window and the real `gauge_core.runner` process running an actual instrument YAML.
